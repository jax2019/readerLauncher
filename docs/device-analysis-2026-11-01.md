# 掌阅 Neo 3 Ultra 耗电分析与桌面方案

采集日期：2026-11-01，Asia/Shanghai。用户反馈：待机和微信读书使用过程中均感到耗电偏高。

本文记录最初的设备诊断和方案分析，以及开发者选项的启用过程。以下状态以最初采集时为准；后续已完成的桌面与省电助手实现、实际配置和验收结果见 [项目说明](../README.md)。

## 设备与分析边界

| 项目 | 实机结果 |
| --- | --- |
| 型号 | 掌阅 Neo 3 Ultra / RM06L-CKDW |
| 系统 | Android 14，API 34，厂商 userdebug 固件 |
| 平台 | MTK，系统报告 mt6768 / mt8786 |
| 显示尺寸 | 1072 × 1448，系统密度 240 dpi |
| 微信读书 | `com.tencent.weread.eink`，墨水屏版 2.1.2 |
| 最初默认 HOME | `com.zhangyue.iReader.Eink/.home.ActivityLauncher` |
| 另一个厂商 HOME | `com.szzy.ireader.ink.launcher/.core.LauncherActivity` |
| 诊断权限 | 当前 ADB shell 为 root |
| 采集状态 | 连接电脑并正在充电，最初快照电量约 84% |

这里的 ADB root 只说明当前调试通道的权限，不能据此认定普通新安装的 Launcher 能直接获得 root 或系统签名权限。

本机的 Android 电量模型明显不完整：框架估算容量显示为 1000 mAh，电池学习值约 2946 mAh；CPU 功耗参数为 0，且不支持逐能耗组件的硬件统计。各应用的“估算 mAh”和排行榜不能当作准确的耗电占比，也不能据此判断电池老化。以下优先采用累计放电量、持续时间、唤醒锁和实际文件写入证据。

系统历史时间戳存在校时痕迹，因此以统计持续时间为主要依据，不把早期绝对日期解释为连续使用日期。

## 历史放电基线

来自第一次保存的 `dumpsys batterystats --charged`，统计窗口约 19 小时 43 分钟：

| 场景 | 累计时长 | 放电量 | 电量变化 | 平均速度 |
| --- | --- | --- | --- | --- |
| 息屏 | 18 小时 31 分 50 秒 | 147 mAh | 约 5 个百分点 | 约 7.9 mAh/小时，约 0.27 个百分点/小时 |
| 亮屏 | 1 小时 11 分 21 秒 | 265 mAh | 约 9 个百分点 | 约 223 mAh/小时，约 7.6 个百分点/小时 |
| 合计 | 19 小时 43 分 11 秒 | 412 mAh | 约 13–14 个百分点 | 混合使用，不直接外推整机续航 |

亮屏阶段包含各种操作，微信读书前台累计约 21 分钟，因此 **7.6 个百分点/小时是所有亮屏使用的平均值，不是微信读书专属耗电测试结果**。息屏统计也混有短时唤醒，不能等同于整个窗口完全无人操作的纯待机。

本次窗口约 93.9% 的放电时间开启了省电模式，所以息屏基线已经包含厂商省电效果。当前省电模式关闭的原因显示为接入电源，不能把这个状态直接认定为之前的耗电原因。

## 已确认的优化机会

### 1. MTK 调试日志正在自动录制并持续写盘

证据相互吻合：

- 固件为 `userdebug`，`ro.debuggable=1`。
- `com.debug.loggerui` 的配置为 `mobilelog_autostart=true`。
- 配置文件中 `com.mediatek.log.mobile.enabled=true`，`AllMode=true`。
- `mobile_log_d` 原生进程正在运行；日志录制的结束时间记录为 0。
- `/data/debuglogger/mobilelog` 从 328242 KiB 增至 328822 KiB，约 321 MiB，并持续增长。
- 两次读取 `/proc/968/io`，累计 `write_bytes` 从 343060480 增至 343683072，增加约 608 KiB。

这能够确认存在额外的持续日志处理和存储写入，是优先关闭的功能。它到底贡献多少耗电仍须通过关闭前后的对照测试确定，现阶段不能称为唯一或最大原因。

实施时应通过 MTK 日志控制入口停止录制、关闭自动录制，并验证文件增长和进程写入停止。原生守护进程由 init 启动，仅禁用 `com.debug.loggerui` 这个界面应用，不足以证明录制停止。Android 基础 `logd` 与这套额外落盘录制需要区分处理。

### 2. Android 原生 Doze 的轻度与深度模式均被关闭

`dumpsys deviceidle` 明确显示：

```text
mLightEnabled=false  mDeepEnabled=false
```

这会减少 Android 原生对息屏后台任务和联网的限制，值得做兼容性对照。但厂商也有自己的省电机制，不能简单断言打开 Doze 就一定显著改善续航。

同时，息屏 18 小时 31 分钟内的 CPU 醒着时间只有约 25 分 36 秒，约占 2.3%，说明其余大部分时间确实进入了系统休眠。**Doze 后台限制和内核休眠是两个层面，当前证据不支持“设备整夜完全没睡”。**

内核累计还有 155 次休眠成功、37 次失败，其中冻结阶段失败 27 次，最后一次失败步骤为 freeze。这个累计计数缺少当前窗口归因，后续应在拔线待机前后看增量，确认失败是否持续发生，再追查具体进程或驱动。

建议先验证轻度 Doze 与原厂合盖、唤醒、前光和 Wi-Fi 恢复是否兼容，再考虑深度模式，不直接把强制 idle 当作日常工作方式。

### 3. 联网切换带来了可见的额外唤醒

历史部分唤醒锁：

| 唤醒锁 | 累计时间 | 次数 |
| --- | --- | --- |
| `ConnectivityService` | 约 12 分钟 | 12 |
| `wifi-powerui-Wakelock` | 约 8 分 53 秒 | 统计计数不足以直接解释次数 |

两个唤醒锁可能重叠，不能直接相加解释为额外耗电时长。

观察到 17 条 Wi-Fi 连接事件，多数连接成功且发生在亮屏时。历史 Wi-Fi 状态约 93.2% 为断开；厂商已有息屏关闭 Wi-Fi 的相关设置，扫描始终可用也已关闭。当前信号较强，连接通过网络验证，没有证据把弱信号或整夜不停扫描认定为主因。

适合测试“提前下载章节、阅读时离线、需要同步时再联网”，并观察频繁开合盖时的联网恢复成本。需保留微信读书下载、登录和阅读进度同步的可用性。

蓝牙目前开启，若不用耳机、键盘和翻页器，可以关闭；现有蓝牙唤醒时间较短，暂时没有证据说明它是主要耗电源。

### 4. 原桌面挂有定时更新组件

应用小组件更新闹钟累计有 39 次唤醒。厂商桌面仍绑定了时钟、最近应用、最近阅读、最近书籍和推荐书籍等 5 个组件，其中时钟更新间隔为 30 分钟。

新桌面可以不接入这些推荐内容和小组件，并避免息屏定时更新。仅更换默认 HOME 不保证旧组件注册与后台服务自动消失，需要在实施时单独检查。

### 5. 阅读耗电还需要独立测量前光和刷新的影响

微信读书已经使用墨水屏版；采集时的短时间静止页面样本没有出现持续占满 CPU 的情况。它累计前台约 21 分钟、UID CPU 时间约 10 分 43 秒，包含排版、启动、子进程及后台等活动，不能直接当成异常循环证据。

建议验证的变量包括：前光开/关、联网/离线、点击翻页/滚动、适合文本的刷新模式，以及静止页面是否还在持续提交绘制。

设备同时存在 Android 通用亮度、厂商冷暖光设置和驱动读数，多组值含义不一致，当前不能准确换算成实际前光百分比。系统显示接口报告的 84 Hz 也不能解释为墨水屏每秒实际全刷 84 次，不应直接套用手机的强制刷新率参数。

## 官方书城可以怎样屏蔽

书城不是一个独立的 APK。清单确认：

```text
com.zhangyue.iReader.Eink.Activity.alias.ActivityAliasBookStore
  → com.zhangyue.iReader.Eink.home.ActivityLauncher
```

也就是说，书城入口指向的就是当前官方 HOME 所在 Activity。该包还包含本地阅读、文件管理、账号与数据 Provider、桌面组件等功能，并使用 `android.uid.system/1000`。

由此建议按下面顺序实施：

1. 新桌面仅展示选定应用，把书城和推荐入口从日常界面移除。
2. 检查并按需关闭书城专用入口组件；这只能限制入口，不能证明内部服务和网络请求全部停止。
3. 如果仍需要限制官方业务联网，先确认能按组件或进程边界处理。对 UID 1000 整体断网会波及其他系统服务，不适合用于单独屏蔽书城。
4. 只有完成依赖、重启、合盖唤醒和阅读功能验证后，才考虑整个主包的冻结。

其他可按个人需求评估的独立功能：

| 功能 | 包名 | 建议 |
| --- | --- | --- |
| AI 功能 | `com.szzy.ireader.ink.ai` | 不使用时作为冻结候选，验证快捷入口依赖 |
| 智能助手 | `com.szzy.ireader.smartassistant` | 不使用时作为冻结候选，验证按键与系统入口依赖 |
| 应用市场 | `com.szzy.ireader.ink.appmarket` | 可隐藏，后续考虑冻结；同样共用 UID 1000 |
| 音乐播放器 | `com.szzy.ireader.ink.musicplayer` | 不听音乐时作为候选 |
| 掌阅 TTS | `com.szzy.ireader.ink.tts` | 确认不用朗读、无障碍或其他应用调用后再处理 |
| 翻译词典 | `com.szzy.ireader.ink.translatelexicon` | 确认不用查词、翻译后再处理 |
| OTA 更新 | `com.szzy.ireader.ink.ota.redstone` | 优先控制自动检查，保留手动更新路径 |

候选功能尚未逐包做依赖测试，不能等同于“已证实可安全全部禁用”。仅有后台进程或占用内存，也不代表持续消耗大量电量。

原厂 SystemUI、墨水屏刷新与电源相关组件、设置、输入法、安装器和下载服务，应保留作为基础能力。

## 自定义 Launcher 可行性与第一版范围

本机能解析标准 Android HOME，已经存在两个厂商 HOME 实现，因此开发普通第三方 Launcher 有较高可行性。无需先改 ROM 或替换系统分区。实际实施仍需验证默认桌面选择在冷启动和合盖唤醒后是否保持。

建议做一个原生 Android 桌面，以黑白文字和大按钮为主，第一版包括：

- 微信读书作为主要入口。
- 可配置的常用应用白名单。
- 掌阅设置、Android 系统设置、开发者选项。
- Wi-Fi、蓝牙、阅读灯、应用显示/刷新设置的快捷入口。
- 仅前台需要时更新电量与日期，支持手动刷新。
- 保留返回原厂桌面的维护入口。

使用原生 View 即可满足需求。页面没有秒针、动效、联网推荐或常驻轮询；仅在可见或系统事件到来时更新界面。正常桌面模块不申请唤醒锁。

已从实机清单确认以下入口：

| 用途 | Intent / 组件 |
| --- | --- |
| 掌阅设置 | `com.szzy.ireader.settings/com.szzy.ireader.settings.MainActivity` |
| 阅读灯设置 | `com.szzy.ireader.ink.devicesetting.READING_LIGHT` |
| 应用显示设置 | `com.szzy.ireader.ink.devicesetting.APP_DISPLAY` |
| 开发者选项 | `android.settings.APPLICATION_DEVELOPMENT_SETTINGS` |

前两个厂商专用设置 action 对应的页面组件已导出，但其具体打开效果仍需在新桌面里验证。

普通 Android 14 应用不能随意直接切换 Wi-Fi、冻结系统应用或改受保护的系统设置。第一版通过系统或厂商设置页面操作；深度优化由单独的 ADB/受控权限操作完成，避免让桌面本身依赖一个常驻 root 后台服务。

新桌面主要改善使用体验、减少桌面推荐和小组件开销。微信读书在前台运行时的主要耗电仍须通过阅读配置和系统后台策略优化。

## 开发者选项：本轮已完成的改动

原始状态为：

```text
development_settings_enabled = null
adb_enabled = 1
```

系统开发者 Activity 默认不可用，设置开关后仍不能启动，因此另外启用了它的组件：

```sh
# 启用系统开发者选项及其页面入口。
adb shell settings put global development_settings_enabled 1
adb shell pm enable --user 0 'com.android.settings/.Settings$DevelopmentSettingsDashboardActivity'

# 打开开发者选项。
adb shell am start -a android.settings.APPLICATION_DEVELOPMENT_SETTINGS
```

已验证：标准 action 成功解析为开发者 Activity，Activity 处于前台，屏幕截图显示“开发者选项”且总开关已开启。后续新桌面可直接提供这个入口；本轮没有新增桌面 APK 或永久桌面图标。原厂定制设置列表是否展示它，仍取决于原厂界面实现。

需要恢复本轮改动时，可使用：

```sh
# 恢复修改前未设置该键、组件使用清单默认状态的情况。
adb shell settings delete global development_settings_enabled
adb shell pm default-state --user 0 'com.android.settings/.Settings$DevelopmentSettingsDashboardActivity'
```

## 推荐实施与验收顺序

1. 停止 MTK 额外日志录制和自动录制，验证写入停止、重启后仍关闭。
2. 建立不连接电脑的基线：合盖待机 8–12 小时；固定书籍、字体和翻页节奏阅读至少 60 分钟，必要时延长以超过电量刻度误差。
3. 分别测试阅读时前光与联网的影响，保持其他条件一致。使用起止电量、可用的电荷计数和统计增量比较，不清空现有历史记录来掩盖基线。
4. 安装新桌面并设置为默认 HOME，验证开机、HOME、返回、合盖唤醒、设置与开发者入口。
5. 分批冻结明确不用的独立功能，每批保存原状态、验证关键功能，再做耗电对照。
6. 试验恢复原生 Doze，评估它与厂商省电策略的兼容性和实际收益。

待机测试中保持温度、网络和蓝牙条件接近，避免一边持续 ADB 轮询一边测试休眠。USB 仍连接时的“模拟拔电”不能代替实际断开供电和调试连接。

现阶段可以确认持续调试日志、后台限制配置和联网唤醒都值得优化，但尚未完成任何省电措施的前后对照，不能承诺节省比例或新的续航天数。

原始诊断保存在项目 `diagnostics/2026-11-01-initial/`，包含系统状态与网络信息，已通过项目 `.gitignore` 排除。
